# Egoboo PortMaster port -- developer notes

Build/technical reference for anyone maintaining or rebuilding this port. Not shipped to players; see `README.md` for that.

## What this is

Egoboo 2.8.1, a 2008-era SDL 1.2 + fixed-function OpenGL dungeon crawler. Source ships with a working Linux `Makefile` already (`platform/file_linux.c`/`sys_linux.c` exist), so this is a genuine native aarch64 cross-build, not a Wine/box64 port.

## Build environment

Built inside `/opt/arm64chroot` (a real aarch64 Ubuntu 20.04 rootfs run via `qemu-aarch64-static`, the same chroot used for `flaw`/`teeworlds`/`opensiege`), **not** cross-compiled from the x86_64 host. Since the chroot's own architecture is aarch64, plain `apt install` there installs native aarch64 packages directly -- no multiarch/cross-toolchain juggling needed. If `chroot /opt/arm64chroot ...` fails with `Exec format error`, the qemu binfmt handler isn't registered for this WSL session (`update-binfmts --enable qemu-aarch64` as root; doesn't persist across a WSL restart).

```
apt-get install -y libsdl1.2-dev libsdl-image1.2-dev libsdl-mixer1.2-dev libsdl-ttf2.0-dev libphysfs-dev libenet-dev
cd src && make        # top-level Makefile builds enet then game/egoboo-2.x
```

Needed one fix: the Makefile's `LDFLAGS` is missing `-lm` (`menu.c` calls `log()`), which only shows up as a link error, not a compile error -- added it directly to `game/Makefile`.

### Trimmed SDL_mixer -- the actual reason this wasn't a `flaw`-style 17-file bundle

Egoboo's own bundled `basicdat/`/`modules/` data is 100% OGG (music) and WAV (sound effects) -- checked with `find ... | sed 's/.*\.//' | sort | uniq -c`, zero `.mid`/`.mod`/`.xm`/`.flac`/`.mp3` files anywhere. Ubuntu's distro `libsdl-mixer1.2-dev` package is built with MOD (mikmod) and MIDI (FluidSynth) support on by default, and FluidSynth's own dependency chain is enormous -- `readelf -d` on the stock `.so` shows hard `NEEDED` entries on `libjack.so.0`, `libpulse-simple.so.0`, `libsndfile.so.1`, `libreadline.so.8`, `libinstpatch-1.0.so.2`, `libglib-2.0.so.0`, `libgobject-2.0.so.0`, `libgmodule-2.0.so.0`, `libdbus-1.so.3` -- none of which exist on a ROCKNIX handheld, and bundling that whole desktop-Linux audio/IPC stack for a game that never plays a single MIDI file would be absurd. Rebuilt SDL_mixer 1.2.12 from source (already present in the chroot at `/root/SDL_mixer-1.2.12`) with everything but WAVE+OGG disabled:

```
./configure --disable-music-mod --disable-music-midi --disable-music-timidity-midi \
  --disable-music-native-midi --disable-music-fluidsynth-midi --disable-music-flac \
  --disable-music-mp3-mad-gpl --enable-music-wave --enable-music-ogg
make
```

Result: `readelf -d` on the trimmed `.so` shows only `libSDL-1.2.so.0`/`libc.so.6`/`ld-linux` -- OGG support loads `libvorbisfile.so.3` via `dlopen()` at runtime (real SDL_mixer 1.2 `OGG_DYNAMIC` behavior, not a link-time dependency), and that library is already on both target devices.

### SDL 1.2 itself -- sdl12-compat, not a real SDL 1.2 build

ROCKNIX ships no SDL 1.2 at all (only SDL2/SDL3), and real SDL 1.2 predates KMS/DRM entirely (X11/DGA/fbcon only) so a genuine SDL 1.2 build wouldn't find a display on a modern handheld anyway. Linked against Ubuntu's real `libsdl1.2-dev` headers at build time (same ABI, doesn't matter which implementation actually built against), but the port **ships** the chroot's already-built `sdl12-compat` (`/root/sdl12-compat/build/libSDL-1.2.so.0`) as `libs.aarch64/libSDL-1.2.so.0` -- a real SDL 1.2 API surface translated onto the device's own patched system SDL2. Never bundle a real SDL2 alongside this shim (standard project rule) -- it isn't here.

### Minimal `libs.aarch64/` -- checked against both real devices, not assumed

Every "does the device already have this" question was answered by actually `ls`-ing `/usr/lib/` over SSH on both the X55 and R36S (identical ROCKNIX 20260801 build) rather than copying another port's bundle wholesale. Real result: only 8 files needed bundling, everything else (including `libGLU.so.1`, `libenet.so.7`, `libfreetype.so.6`, `libjpeg.so.8`, `libpng16.so.16`, `libvorbis*`, `liblzma.so.5`, `libzstd.so.1`, `libstdc++.so.6`) was already present with a matching SONAME on both devices:

```
libSDL-1.2.so.0        (sdl12-compat build, see above)
libSDL_mixer-1.2.so.0  (trimmed build, see above)
libSDL_ttf-2.0.so.0    libSDL_image-1.2.so.0    libphysfs.so.1
libtiff.so.5  libjbig.so.0  libwebp.so.6         (device has libwebp.so.7 -- SONAME bump, must bundle .so.6)
```

## Real-hardware debugging -- three real bugs, none of them build bugs

`chroot`/`make` success proves nothing about runtime behavior (standard caveat) -- all three of these only showed up running the actual `Egoboo.sh` over SSH on the X55.

**1. Silent `exit(255)` right after filesystem init, no crash, no further log line.** `printf()`-based messages (all in `platform/file_linux.c`'s `sys_fs_init()`) go to stdout; everything after that (`log_message()`/`log_info()` -- literally every other startup line) goes **only** to `$HOME/.egoboo-2.x/debug/log.txt`, never stdout. Chasing this via `gdb -batch -ex run -ex bt` was a dead end (`exited with code 0377`, no stack -- a clean `exit()`, not a crash) until checking that log file directly showed the real, specific SDL error text. **Lesson for next SDL1.2 port: always check `$HOME/.egoboo-2.x/debug/log.txt` (or whatever the game's own log path is), not just stdout, before reaching for gdb.**

**2. `basicdat`/`modules`/`setup.txt`/`controls.txt` need to resolve relative to cwd, not the compiled-in `/etc/egoboo-2.x`+`/share/games/egoboo-2.x`.** The stock Makefile always defines `_NIX_PREFIX` (its own `ifdef ($(PREFIX),"")` guard is malformed GNU Make and never takes the true branch), embedding absolute Linux-distro-style paths that don't exist in a PortMaster install. Patched `platform/file_linux.c`'s `sys_fs_init()` to force both `linux_configPath` and `linux_dataPath` to `"."` right after the `#endif`, unconditionally -- the launch script already does `cd $GAMEDIR` first, so `.` is exactly `$GAMEDIR`. `fs_getUserDirectory()` (`$HOME/.egoboo-2.x`, for saves) was left alone -- that's controlled entirely by the launch script's own `export HOME="$GAMEDIR/conf"`, no source patch needed.

**3. `gl4es.$DEVICE_ARCH` must be on `LD_LIBRARY_PATH`, not just pointed at by absolute path in `SDL_VIDEO_GL_DRIVER`/`SDL_VIDEO_EGL_DRIVER`.** This is the one that cost the most time. Egoboo's renderer is fixed-function desktop GL only (`glBegin`/`gluPerspective`/`gluLookAt` all over `extensions/ogl_include.c`) -- confirmed real hardware needs gl4es unconditionally even on this Panfrost-driven X55 build, which reports real desktop OpenGL 3.1 to a generic capability probe: going through the system's own GL/EGL directly (no gl4es at all) makes `SDL_VideoModeOK()` itself return 0 for an `opengl`-flagged mode, meaning SDL2's `kmsdrm` backend only ever negotiates GLES contexts regardless of what the GPU can otherwise do. So gl4es is required -- but this project's usual `libgl_${CFW_NAME}.txt`/`libgl_default.txt` helper files (referenced by every other port's Pattern B script) **don't exist at all on this ROCKNIX build** (`cat`/`source` on either path just silently fails), so `LD_LIBRARY_PATH` was never getting `gl4es.$DEVICE_ARCH` added, even though `SDL_VIDEO_GL_DRIVER`/`SDL_VIDEO_EGL_DRIVER` were set to the exact right absolute file paths. Real-hardware symptom: `gl4es`'s own internal init succeeded completely (all its extension-detection log lines print fine, using the real system `libGLESv2.so`/`libEGL.so`/`libgbm.so`/`libdrm.so` via bare `dlopen()`), but then `SDL WARN: Unable to set SDL video mode: Could not load EGL library` -- because `libEGL.so.1` (the file *we* ship in `gl4es.$DEVICE_ARCH`) has a bare (no-path) ELF `NEEDED` on `libGL.so.1`, and without our own `gl4es.$DEVICE_ARCH` on `LD_LIBRARY_PATH`, the dynamic linker resolved that to the *system's real Mesa* `libGL.so.1` instead of gl4es's own paired one -- a mismatched pairing that breaks gl4es's EGL init from the inside. Fix: `Egoboo.sh` now unconditionally does `export LD_LIBRARY_PATH="$GAMEDIR/gl4es.${DEVICE_ARCH}:$LD_LIBRARY_PATH"` itself instead of assuming a CFW-provided helper file exists.

**gl4es binaries are reused as-is from the already-working `teeworlds` port** (`libGL.so.1`/`libEGL.so.1`, same architecture, same "fixed-function desktop GL, no native GLES path" shape) -- no separate gl4es build needed for this port.

## Resolution / fullscreen

Egoboo only reads its bundled `setup.txt` (this port's shipped default) on the **very first run ever** -- `fs_ensureUserFile()` copies it into `$HOME/.egoboo-2.x/setup.txt` once, and every later launch reads that persisted copy instead, ignoring further edits to the bundled file. The bundled default ships a conservative `640x480`, but real-hardware testing showed that requesting a resolution that doesn't match the compositor's actual output size doesn't get scaled -- sdl12-compat's SDL1.2 fullscreen path just places the smaller buffer top-left, leaving black bars filling the rest of the screen (confirmed live: a 640x480 request on the X55's 1280x720 panel rendered as a small window in the corner). Fix: `Egoboo.sh` `sed`-patches just the `SCREENSIZE_X`/`SCREENSIZE_Y` lines of the **persisted** `$HOME/.egoboo-2.x/setup.txt` to the real `$DISPLAY_WIDTH`/`$DISPLAY_HEIGHT` on every single launch (creating that file from the bundled template first if it doesn't exist yet) -- self-healing on every run, and doesn't touch any other setting the player has changed from the in-game Options menu. Confirmed via `grim` screenshot on both the X55 (1280x720) and R36S (its own native res) that this produces a correctly full-screen, non-cropped main menu on both.

## Controls

Native `SDL_JoystickOpen()` reading disabled entirely (`input.c`'s `input_init_joysticks()` call commented out) -- the game's own `controls.txt` hardcodes raw `JOY_0`..`JOY_7` button-index bindings for Left/Right Hand Use/GetDrop/Inventory, which would otherwise fire from the exact same physical button press gptokeyb2 already translated into a synthetic keyboard event, a real double-input bug (same class as the classic-gptokeyb trap, but from the game engine's own native joystick code this time, not gptokeyb itself). `SDL_InitSubSystem(SDL_INIT_JOYSTICK)` itself was left alone (harmless, no `SDL_JoystickOpen` follows it) rather than also removing that call, to keep the diff minimal.

Button layout follows the project's Tier-1/Tier-2 framework (§1.8.4 of the master reference): Jump on A, the single most-used attack (Right Hand Use) on X as the A+X pair, Left Hand Use on B, Right Hand Get/Drop (loot, frequent in this game) on Y. Left stick emulates the mouse (see below), R2 is mouse-click. Right stick is deliberately left unbound -- see the camera-rotate bug below.

## Real-device bugs found after initial packaging (real controller in hand)

**Main menu (New Game/Load Game/Options) is 100% mouse-driven, no keyboard fallback at all.** Confirmed by reading `menu.c` directly: every button on the main menu screen is a `ui_doButton(...)` call, and only the "Quit" button also checks `SDLKEYDOWN(SDLK_ESCAPE)` as an alternate -- "New Game"/"Load Game"/"Options" have no keyboard equivalent whatsoever. The first shipped `egoboo.ini` had zero mouse emulation (all-keyboard, matching `controls.txt`'s Keyboard scheme for actual dungeon gameplay), which meant the game was **completely unusable** past the main menu with a real controller -- confirmed by the person testing on hardware, not caught by any of the SSH/screenshot verification done during initial build (a static main-menu screenshot looks identical whether or not the menu is clickable). Fix: `left_analog = mouse_movement` plus `r2 = "mouse_left"` in `egoboo.ini`, on top of (not replacing) the existing keyboard bindings used once an actual module is loaded.

**D-pad right caused a full black screen while held; the camera and character models never fully recovered.** This took a full AddressSanitizer-instrumented rebuild and live `gdb` (hardware watchpoints, live struct dumps) on real hardware to actually root-cause, because it wasn't one bug -- it was four, stacked, and only the last one was the actual visual symptom people would call "the bug":

1. **`mesh.c` `mesh_make_normals()`: `ix_off[4-j]`/`iy_off[4-j]` read one past the end of a 4-element stack array when `j==0`** (the surrounding loop already uses the correct `[(4-j+k)%4]` pattern two lines later -- these two just forgot the modulo). Caught by ASan as a stack-buffer-overflow crash on module load, before gameplay was even reachable. Fixed by adding the missing `%4`.
2. **`enchant.c` `cleanup_enchant_list()`: indexed `enc_used[ienc_nxt]` before checking `ienc_nxt` against the `MAX_ENC` end-of-list sentinel**, overflowing the `enc_used[MAX_ENC]` array by one every time the enchant list legitimately terminated. Same off-by-one shape as #1, different array. Fixed with a `VALID_ENC_RANGE(ienc_nxt) &&` guard.
3. **`graphic.c` `dolist_add_chr()`: never reset `pinst->indolist` back to `bfalse` when it decided *not* to add a character to the frame's draw list.** Once a character's tile happened to drop out of the renderlist for even one frame (see #4), this stale `true` flag permanently short-circuited every future `dolist_add_chr()` call for that character (`if (pinst->indolist) return gfx_success;` at the top of the function, before ever touching the array again) -- the character became invisible forever, even after its tile was visible again, confirmed live via `gdb`: character `alive=true`, `on=true`, correct tile `inrenderlist=true`, `indolist=true`, yet absent from the current frame's dolist. This is what caused the player and both followers to vanish permanently (leaving only their held-torch particle effect) instead of just flickering. Fixed by explicitly clearing the flag in `dolist_make()`'s per-character fill loop, right before each character's own `dolist_add_chr()` call, instead of relying on the previous frame's array contents to self-report who needs clearing.
4. **The actual trigger, and the real "black screen" cause: `bool_t` compiles to `enum e_bool` in C, and GCC picks `unsigned int` as its underlying type** (legal, since both enumerators `bfalse=0`/`btrue=1` are non-negative). Several places in `camera.c`/`game.c` compute a signed direction from two `control_is_pressed()` calls, e.g. `(control_is_pressed(...CONTROL_LEFT) - control_is_pressed(...CONTROL_RIGHT)) * CAM_TURN_KEY`. When only `CONTROL_RIGHT` is pressed, that's `0u - 1u` in **unsigned** arithmetic, which wraps to `0xFFFFFFFF` (~4.29 billion) instead of `-1`. Multiplied into `pcam->turnadd`, this produced a turnadd of ~6.44e10 in a single frame (`4294967295 * CAM_TURN_KEY(15) = 64424509425`, exact match) -- caught live with a conditional `gdb` hardware watchpoint (`watch PCamera->turnadd`) that broke the instant the value jumped. That corrupted turnadd feeds directly into `pcam->pos`/`center`, producing a nonsensical camera transform, which correctly (!) makes `gfx_project_cam_view()` compute a fully degenerate frustum and `renderlist_make()` legitimately return 0 visible tiles -- a real screen-goes-black, not a rendering bug. **Never triggers on left** because `1u - 0u = 1`, no wraparound -- pure left/right asymmetry from unsigned underflow, not a camera-math bug at all. The *identical* pattern in `game.c`'s movement code (`joy_pos.y = CONTROL_DOWN - CONTROL_UP`) was the separate, previously-reported "D-pad up and down both move forward" bug: the wrapped huge value survives the immediately-following vector normalize with the wrong sign, so holding Up produced the same movement direction as holding Down. Fixed all five call sites (`camera.c`: turn, camera-look L/R, zoom in/out; `game.c`: strafe, forward/back) with an explicit `(int)` cast on each `control_is_pressed()` operand before subtracting. This is a genuine latent bug in the original 2008 Egoboo source, not something this port introduced -- it just never got exercised this way on a keyboard-only desktop control scheme.

Root-caused with a dedicated ASan build (`libasan.so.5` + a small `dlopen()` interposer stripping `RTLD_DEEPBIND`, since gl4es's own `dlopen()` call is otherwise incompatible with ASan interception) launched through the real `Egoboo.sh` (a bare SSH run of the binary fails a video-mode check that only succeeds via the full launch chain, for reasons unrelated to ASan -- `pm_platform_helper` does something beyond its visible diagnostic print that matters here). All diagnostic scaffolding (`CAMDIAG` checkpoint logging in `camera.c`, ASan Makefile flags, `strip_deepbind.so`, `libasan.so.5`, the temporary `Egoboo_asan_test.sh`) has been removed/reverted; the binary shipped from here on is a plain `-Os` stripped release build with only the five real source fixes above baked in.

**Zoom (`right_analog_up`/`_down` -> `"="`/`"-"`) was always fine and is kept** -- it changes `cam->zaddgoto` (distance), a different code path from the turn/strafe bugs above. `right_analog_left`/`_right` are deliberately left unbound (manual camera rotation isn't load-bearing; auto-turn already handles it) -- not because rotation was unfixable, just not worth wiring a control-pad axis to a feature the game doesn't need pad access to.

## Known follow-ups (not yet done)

- `cover.png` not made yet.
- Multiplayer/network play (`network.c`, real `enet` usage) is untouched/untested -- this port targets single-device single-player only, consistent with every other port in this project.
- The `control_is_pressed()` boundary check in `input.c` (`if (pdevice->count < icontrol) return retval;`) has the same off-by-one shape as bugs #1/#2 above (should be `<=`) and can read one past `pdevice->control[]` when `icontrol == count`. Not currently reachable by any call site in this build (checked: every `CONTROL_*` value passed to it stays under the relevant device's `count`), so left as-is rather than risk an unrelated change this late -- worth fixing if this code is touched again.
